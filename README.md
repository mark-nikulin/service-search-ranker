# Service Search Ranker: Двухстадийная система поиска и рекомендаций услуг

ML-пайплайн ранжирования и рекомендаций для крупной платформы объявлений и услуг (Service Marketplace N). Проект реализован в рамках фриланс-задачи по модернизации поисковой выдачи: переход от классических эвристик к современному двухстадийному подходу (Candidate Retrieval + Re-ranking), что позволило существенно повысить релевантность выдачи и качество рекомендаций для пользователей.

Ключевой результат на отложенном тестовом бенчмарке: **Recall@50 = 0.8756** (87.56% релевантных услуг попадают в топ-50 выдачи).

---

## 🎯 Бизнес-контекст и задача

Платформа N предоставляет пользователям поиск исполнителей и предложений услуг по текстовым запросам, геолокации и параметрам (фильтрам). Исходная система поиска часто выдавала нерелевантные или географически недостижимые результаты при сложных или редких запросах.

### Основные вызовы задачи:
1. **Холодный старт каталога**: ~90% объявлений в тестовом бенчмарке отсутствовали в исторических логах взаимодействия (train). Полагаться на ID-признаки объявлений невозможно — требовалось моделировать контентные признаки, семантику и метаданные.
2. **Географическая специфика и региональный дисбаланс**:
   - В 83% случаев пользователи выбирают услугу строго в своей локации.
   - В 17% случаев запрос формируется из небольших городов/районов («регион»), где прямых предложений нет, и поиск должен охватывать близлежащие центры.
3. **Лексическая вариативность**: Разные формулировки одной потребности («автоподбор» ↔ «диагностика и осмотр автомобиля перед покупкой», «скупка» ↔ «срочный выкуп»), а также опечатки пользователей.
4. **Ограничения по ресурсам**: Необходимость работы с корпусом из сотен тысяч объявлений с умеренным потреблением оперативной памяти (пик до ~5 ГБ RAM) и возможностью локального инференса.

## 🏗 Архитектура решения

Решение построено по проверенной индустриальной двухстадийной схеме:

```
[Поисковый запрос + Гео + Фильтры]
                │
                ▼
   ┌────────────────────────────────────────────────────────┐
   │ Stage 1: Гибридный Ретривер (Candidate Generation)     │
   │  • Вероятностная матрица гео-переходов                 │
   │  • TF-IDF по стемам (заголовки, параметры, описания)   │
   │  • Буквенные n-граммы (устойчивость к опечаткам)       │
   │  • kNN Query Expansion (обогащение запроса по логам)   │
   │  • Плотные семантические эмбеддинги (multilingual-e5)  │
   │                                                        │
   │  Результат: отбор ~600 наиболее перспективных          │
   │             кандидатов на каждый запрос                │
   └────────────────────────────────────────────────────────┘
                │
                ▼
   ┌────────────────────────────────────────────────────────┐
   │ Stage 2: Градиентный Бустинг (Re-ranking)              │
   │  • HistGradientBoostingClassifier                      │
   │  • ~70 признаков (абсолютные и внутризапросные)        │
   │  • Query-relative нормализация (ранг, gap от топ-1)    │
   │  • Сигналы качества: рейтинг, отзывы, цена, фильтры    │
   │                                                        │
   │  Результат: итоговый отранжированный топ-50            │
   └────────────────────────────────────────────────────────┘
                │
                ▼
      [Топ-50 Релевантных Услуг]
```

### 1. Stage 1: Кандидатогенерация (Retriever)
* **Гео-пул на матрице переходов**: Вместо жесткого фильтра по локации построена матрица вероятностей переходов `P(локация объявления | локация поиска)`. Это обеспечило потолок полноты пула (Recall ceiling) на уровне **98%**, решив проблему пустой выдачи для 17% запросов из регионов.
* **Лексический матчинг (Snowball TF-IDF)**: Быстрые разреженные скалярные произведения по стеммированным текстам для заголовков, структурированных параметров и начала описаний.
* **Символьные n-граммы**: TF-IDF по буквенным n-граммам заголовка для защиты от опечаток и морфологических искажений.
* **Query Expansion через kNN**: Поиск семантически близких исторических запросов и построение профиля объявлений, которые по ним выбирали. Позволяет модели связать синонимичные термины без ручных словарей.
* **Семантический векторный поиск**: Предобученная модель `intfloat/multilingual-e5-small` генерирует 384-мерные эмбеддинги для объявлений и запросов. Косинусное сходство улавливает глубокий смысл даже при полном несовпадении ключевых слов.
* **Многоканальный отбор кандидатов**: Объединение кандидатов по взвешенной линейной смеси с топами по каждому независимому сильному сигналу (гарантирует, что сильное семантическое совпадение не потеряется).

### 2. Stage 2: Ранжирование (Ranker)
* **Модель**: `HistGradientBoostingClassifier` (бинарная классификация вероятности клика / выбора).
* **Feature Engineering (~70 признаков)**:
  - Текстовые и семантические метрики (TF-IDF скоры, косинусы эмбеддингов, покрытие слов запроса).
  - **Внутризапросные относительные признаки (Query-relative features)**: ранг кандидата внутри текущего запроса и отставание (gap) от максимального скора. Такие признаки инвариантны к общей сложности запроса.
  - Метаданные и доверие: рейтинг исполнителя, число отзывов, ценовые диапазоны, совпадение параметров фильтра.

## 📊 Результаты и динамика метрик

Валидационный пайплайн спроектирован так, чтобы строго моделировать реальный бенчмарк и исключить любые утечки данных (Data Leakage):
- Отложенные запросы содержат уникальные тексты.
- Все положительные объявления валидации полностью исключаются из обучающей выборки ранкера.
- Корпус валидации сформирован из 189k объявлений.

| Этап разработки / Конфигурация пайплайна | Валидация (Recall@50) | Тестовый бенчмарк (Recall@50) |
|---|:---:|:---:|
| 1. Базовая линейная эвристика (Baseline) | 0.7030 | — |
| 2. TF-IDF + kNN Query Expansion + GBDT Ranker | 0.8890 | 0.8645 |
| 3. **Полный пайплайн (+ multilingual-e5 embeddings)** | **0.9050** | **0.8756** |

```
├── data/                 # Директория с датасетами (train.parquet, benchmark_*.parquet)
├── cache/                # Кэшированные предобработанные данные и эмбеддинги
├── src/
│   ├── common.py         # Загрузка, потоковая обработка parquet, стемминг, сплиты, метрики
│   ├── embed.py          # Построение эмбеддингов объявлений (multilingual-e5-small)

│   ├── build_val.py      # Генерация валидационных сплитов с признаками
│   ├── cv_ranker.py      # Кросс-валидация качества ранкера (Recall@50)
│   └── make_answer.py    # Финальный пайплайн построения предсказаний топ-50
├── requirements.txt      # Зависимости проекта
└── README.md
```

## 🚀 Воспроизведение и запуск

### 1. Окружение
Требуется Python 3.12:
```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### 2. Данные
Поместите входные данные в папку `data/` (или задайте переменную окружения `DATA_DIR`):
- `train.parquet`
- `benchmark_queries.parquet`
- `benchmark_items.parquet`

### 3. Запуск пайплайна
Шаги выполняются последовательно:
```bash
# 1. Построение кэша текстов и расчет эмбеддингов объявлений (~20 мин на GPU/MPS)
python src/embed.py

# 2. Построение обучающих валидационных сплитов (~4 мин каждый)
python src/build_val.py 0
python src/build_val.py 1
python src/build_val.py 2

# 3. (Опционально) Оценка Recall@50 на кросс-валидации
python src/cv_ranker.py 0 1 2

# 4. Финальный инференс и генерация топ-50 рекомендаций (answer.csv)
python src/make_answer.py
```

## ⚡ Оптимизация производительности и ресурсы

- **Потоковая обработка (Stream Batching)**: Чтение parquet-файлов батчами по 50k строк с отсечением сырых текстов описаний снижает пиковую нагрузку на RAM до **~5 ГБ**.
- **Хранение в памяти**: Использование компактных форматов (`float16` для эмбеддингов, `np.float32` для признаков).
- **Аппаратное ускорение**: Инференс модели E5 поддерживает Apple Silicon (MPS), NVIDIA CUDA и fallback на многопоточный CPU.
- **Автономность**: Веса трансформера скачиваются один раз из Hugging Face Hub, после чего весь пайплайн работает полностью локально без внешних сетевых вызовов.
